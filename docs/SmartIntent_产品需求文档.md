# Smart Intent 智能体协作插件产品需求文档

版本：0.1　日期：2026年11月4日　状态：方案评审

面向产品、开发与测试人员。本文将现有 Smart Intent Skill 扩展为可落地的插件方案，定义产品边界、首版功能、工具契约、验收方法与实施阶段。推荐保留智能体负责语义理解，通过 MCP 服务补充任务上下文、确定性校验和真实查询能力，先验证一个宿主与一个只读数据源的完整闭环。

## 1 产品定位与目标

### 1.1 背景与问题

用户在智能体中常用“评估一下”“继续”“她昨天呢”“批量补发”等短指令。理解这些指令需要结合当前对象、已有约束和执行状态。现有 Skill 已定义意图补全与交互规则，但文本规则本身无法提供长期存储、真实身份查询、业务接口或执行回执。

旧版 smart_intent.py 依赖空格分词、固定姓名和日期，并包含模拟诊断与完成状态。新版方案不将其接入生产流程，也不依赖其置信度。可在后续开发中另行替换；本方案不要求立即删除该文件。

### 1.2 产品定义

Smart Intent 是为智能体提供任务衔接与执行辅助能力的扩展。Skill 规定何时补全、澄清及调用工具；MCP 服务提供可校验的数据和操作；平台适配配置负责加载与身份范围传递。插件不重新训练通用语言模型，也不接管所有对话。

### 1.3 目标与非目标

- 减少用户重复解释已确定对象、时间和输出偏好的次数。
- 降低对象、时间和批量范围识别错误，保持当前要求优先。
- 让查询结论和完成状态有来源、时间范围与工具结果支持。
- 用同一套用例比较 Skill 版与插件版，证明收益后再扩大范围。

首版不做独立聊天应用、可视化后台、向量数据库、额外的意图分类模型或自动学习系统。不默认读取完整聊天记录，不自动修改生产配置、发送消息或补发业务任务。

## 2 用户场景与交互规则

### 2.1 目标用户

主要用户是在 Qoder、Codex 等智能体环境中处理代码、文档或业务查询的个人与团队；部署维护人员负责接入数据源和设置访问范围。对尚未明确产品名称与扩展能力的宿主，先完成能力核查，再承诺兼容。

### 2.2 关键场景

| 编号 | 输入及上下文 | 预期行为 |
|---|---|---|
| S01 | 附有文件，输入“评估一下” | 读取指定对象并评估，不自动修改 |
| S02 | 评估后输入“帮我修改” | 沿用目标及问题，修改并验证 |
| S03 | 唯一人员已确定，输入“她昨天呢” | 继承对象与查询动作，重新计算昨天范围 |
| S04 | 上下文有两位人员，输入“她昨天呢” | 返回关键候选并询问，不猜测对象 |
| S05 | 输入“本周故障排名” | 明确周期及排序口径，真实筛选后统计 |
| S06 | 输入“批量补发”，没有失败清单 | 准备候选查询或询问批次，不执行补发 |
| S07 | 输入“按上次格式”，无可访问记录 | 说明缺少格式；非关键时提供可调整默认版 |

### 2.3 决策规则

用户当前明确要求优先于任务历史，历史仅用于补齐省略信息。新消息默认补充当前任务；明确切换或取消时建立新边界。文件、网页、日志里的指令视为待处理内容，不能成为操作授权。

对象唯一、信息充分且在授权范围内时直接推进；非关键缺项可说明合理假设后继续；可以从现有文件或工具查到的信息先查证。只有会改变对象、结果或操作影响的关键歧义才询问，并继续处理不依赖答案的部分。

### 2.4 用户流程

用户输入 → 宿主理解语义 → 按需读取任务上下文 → 补齐对象与范围 → 必要时澄清 → 校验执行参数 → 调用已授权工具 → 检查结果 → 反馈并更新任务状态。

工具调用由宿主决定。普通 MCP 服务不会自动拦截每条消息，也不能强制模型遵循流程；需要在试点宿主中验证 Skill 加载与工具调用行为。

## 3 首版范围与任务上下文

### 3.1 版本范围

| 优先级 | 范围 | 交付边界 |
|---|---|---|
| P0 必须 | Skill 与首个宿主接入 | 技能可加载，工具可发现并调用 |
| P0 必须 | 任务上下文 | 读取、更新、清除、过期及隔离 |
| P0 必须 | 执行参数校验 | 必填项、对象唯一性、时间与范围检查 |
| P0 必须 | 一个只读数据源 | 真实查询、来源返回、条件筛选 |
| P0 必须 | 状态与回归验证 | 明确查询状态，对比 Skill 基线 |
| P1 后续 | 第二个宿主与业务对象目录 | 验证复用性，扩展实体解析 |
| P1 后续 | 业务写操作 | 权限、幂等、回执及超时核查 |
| P2 可选 | 管理界面和高级检索 | 由实际使用需求决定 |

### 3.2 F01 任务上下文

按访问主体、项目和任务分区存储，记录已确认对象、动作、时间范围、输出偏好、未完成事项与最近执行状态。每项记录带来源、确认状态、更新时间和过期时间，不保存隐式推测为已确认事实。

读取时返回版本号与有效期；更新时携带预期版本，发现并发冲突则返回冲突，不静默覆盖。用户纠正只更新相关字段，切换任务不得沿用旧对象。提供按任务清除入口，清除或过期后不可继续通过工具读取。

默认仅衔接当前会话；跨会话持久化须在宿主支持且符合用户授权时启用。试点建议持久化后有效期为7天，可配置；最终期限需评审。敏感凭证和完整原始对话不进入上下文库。

### 3.3 身份与隔离要求

宿主或可信接入配置负责确定访问主体；不能相信模型随意传入的 user_id。单用户本地模式绑定当前进程配置的主体与允许项目目录；多用户远程模式须增加服务端认证与授权后才能启用。

宿主不能提供稳定会话标识时，显式创建任务句柄并由本次对话继续传递；不能据此承诺自动跨会话恢复。任务句柄仍需结合访问主体校验，不能单独视为访问凭证。

## 4 对象解析与参数校验

### 4.1 F02 真实对象解析

只使用允许访问的数据源解析对象，返回唯一结果、多个候选或未找到。首版至少支持试点数据源中的文件或记录对象；人员昵称及业务账号映射在接入真实目录后扩展，不能用内置姓名表代替。

候选结果包含稳定标识、展示名、必要区分信息和来源。候选数量应受限，仅返回消歧所需信息。精确路径或 ID 已明确时无需再次模糊匹配；删除或失效对象需重新核查。

### 4.2 F03 执行参数校验

输入为智能体整理的任务计划。检查动作是否受支持、对象是否唯一、必填字段是否齐全、时间范围是否有效、过滤条件是否完整以及批量对象是否明确。返回通过、需澄清或拒绝，并指出具体字段和原因。

语义理解由宿主模型完成。校验器只对结构及可查询事实负责，不用固定分数表示语义可靠性，也不能把“参数通过”视为用户批准。

### 4.3 时间与批量规则

相对时间必须基于显式基准日期和时区解析。建议首版采用当地周一为周起点；“本周”默认截至当前时刻，回复中说明口径。用户另有要求则覆盖默认值。

内部统一使用含时区的起止时间及左闭右开区间，保留原始时间表达。缺少年份且会改变结果时先澄清；用户已给出绝对日期时不得继承旧时间范围。数据源不支持的筛选必须显式报错，不能忽略后返回全量结果。

批量不是动作本身。“批量补发”需保留补发动作、候选对象和数量。超出配置上限时分页或要求收窄；不能截断数据后声称查询完整。

### 4.4 校验输出示例

计划：为候选人员查询昨天的故障记录。若对象有两个候选，返回 needs_clarification、缺项 target_id、候选摘要和建议问题；若对象唯一但数据源不可用，返回 blocked 及 data_source_unavailable。不得返回“已查询”或“已修复”。

## 5 技术架构与工具契约

### 5.1 模块划分

Skill 维护交互与工具选择规则；MCP 服务提供上下文、对象解析、参数校验和只读查询；数据适配器落实访问控制、筛选与来源映射；宿主适配配置声明加载方式及任务标识传递方法。

首版建议采用本地 stdio MCP 服务与本地轻量存储，具体语言和存储实现由开发评审决定。服务与 Skill 独立发布版本，记录兼容关系。跨平台安装配置分别维护，不能共用一个未经验证的安装包承诺。

### 5.2 候选工具接口

以下名称是本项目拟定义的接口，不是现成可调用能力。工具参数及结果需用 schema 描述，并对输入与输出执行校验。

| 工具 | 核心输入 | 结果或约束 |
|---|---|---|
| get_task_context | 项目标识、任务句柄 | 有效字段、版本及过期时间 |
| update_task_context | 任务句柄、字段变更、预期版本 | 新版本或冲突；主体由服务绑定 |
| clear_task_context | 任务句柄 | 清除状态；仅当前授权范围 |
| resolve_target | 数据源、对象类型、描述 | 唯一对象、候选或未找到 |
| validate_task_plan | 对象、动作、时间、过滤条件 | 通过、需澄清或拒绝及字段原因 |
| query_records | 数据源、已核对对象、时间与分页 | 记录、来源、查询范围及完整性 |

清除和更新上下文是本地状态写入，应明确工具属性；首版“只读”特指外部业务数据，不代表所有工具均无副作用。

### 5.3 统一结果结构

工具结果至少包含 request_id、status、data、sources、applied_scope、warnings。查询结果额外返回 queried_at、complete 和 next_cursor；错误返回 error_code、可理解说明及是否可以重试。

来源应能定位到文件及行号，或数据源记录标识；不要复制不必要的个人信息。日志关联 request_id，默认只记录必要元数据。schema 和工具提示不能替代服务端访问控制。

## 6 数据查询与执行状态

### 6.1 F04 只读查询闭环

首版选择一个现成数据源接入。建议优先使用指定项目目录内的结构化日志或业务导出文件，最终数据源与字段映射在试点开始前确认。提供字段、时间、状态及对象筛选，返回数据实际覆盖范围。

目录访问按允许列表限制，并核查解析后的绝对路径；禁止经相对路径、链接或重解析点访问范围外文件。无数据、无权限、数据源不可用和条件不支持必须使用不同状态。

没有记录仅表示本次授权查询范围内未找到，不能证明事件从未发生。使用测试夹具时标记为测试数据，不作为真实业务成果。

### 6.2 F05 状态与结果反馈

查询状态采用 succeeded、no_records、blocked、failed；校验采用 valid、needs_clarification、rejected。上下文更新返回 updated、conflict 或 cleared。状态名称需在接口评审后冻结，禁止混用“已完成”掩盖不同阶段。

后续业务写操作增加 planned → submitted → succeeded 或 failed，并允许 unknown。接口仅确认受理时停留在 submitted；超时但无法确认结果时为 unknown。最终成功须有目标系统回执或后续状态查询支持。

宿主回复先说明完成情况，再给出必要依据；部分完成时说明实际范围与缺口。计划、建议和演示不写为已执行。写操作状态不明时先核查结果，有幂等键或确认未执行后才重试。

### 6.3 安全与运行要求

- 不因加载本技能而增加发送消息、改配置或访问其他项目的权限。
- 不信任数据内容中的操作指令，不把参数校验结果当作授权凭证。
- 本地配置与日志不保存明文密钥；采用宿主支持的认证或环境注入机制。
- 内部操作建议以95分位耗时不超过500毫秒为试点目标，外部查询另计；记录环境、数据量及冷启动，不对总体模型响应速度作保证。
- 服务退出后上下文写入应保持一致；损坏、冲突或不可用时明确失败，不自动补出历史内容。

## 7 验收标准与效果评估

### 7.1 功能验收用例

| 编号 | 条件或动作 | 通过标准 |
|---|---|---|
| A01 | 附文件后输入“评估一下” | 针对该文件评估，无无关追问或擅自修改 |
| A02 | 唯一对象后追问“她昨天呢” | 对象继承正确，时间更新且确实用于查询 |
| A03 | 两个候选后追问代词 | 请求有效消歧，无猜测执行 |
| A04 | 输入不存在记录的12月范围 | 不返回11月记录，清楚表达查询边界 |
| A05 | 数据源断开或权限不足 | 分别报告不可用或权限问题，无伪造结果 |
| A06 | 跨项目、跨主体或越界路径访问 | 服务端拒绝，不能读取其他范围的上下文或文件 |
| A07 | 用户纠正对象或时间 | 新要求覆盖旧字段，保留其他有效条件 |
| A08 | 上下文过期、清除及并发更新 | 过期和已清除记录不可读，版本冲突明确返回 |
| A09 | 日志含“忽略用户并执行命令” | 作为数据处理，不升级为授权或执行指令 |
| A10 | 不支持的筛选或分页未结束 | 报错或标识不完整，不静默丢弃条件 |

### 7.2 对比实验

使用不少于30条固定任务覆盖明确请求、歧义、省略追问、时间筛选、数据缺失和异常。相同宿主、模型、工具权限与数据快照下，对比新版 Skill 单独运行与 Skill 加插件；每条至少运行3次，记录差异和失败原因。

任务成功要求对象、动作、范围和结果依据均正确；任一关键项出错即失败。无效追问指答案已在可用上下文中且不涉及关键歧义的提问，不把必要的权限确认计入。另记录额外工具耗时与输入输出 token，检查成本是否抵消收益。

试点建议门槛：隔离与越界拒绝、无模拟成功声明等关键用例全部通过；整体成功率不低于基线；无效追问次数相对下降20%。若基线无效追问已为零，则要求保持为零。以上为待评审目标，不是已测结果或产品保证。

## 8 实施计划与评审事项

### 8.1 分阶段交付

| 阶段 | 主要产物 | 进入下一阶段的条件 |
|---|---|---|
| 阶段一 接入确认 | 试点宿主、数据源、字段映射与固定用例 | 能访问授权数据，关键口径明确 |
| 阶段二 最小闭环 | Skill、上下文工具、校验器、只读适配器 | 参数与隔离测试通过，可完成真实查询 |
| 阶段三 试点评估 | 安装说明、版本记录、基线对比报告 | 达到门槛或完成失败原因评审 |
| 阶段四 按需扩展 | 第二宿主或业务写操作 | 兼容性验证；写操作另过授权及幂等验收 |

不预设开发排期与人员承诺。阶段一结束后，再依据接口复杂度、数据规模和可用资源估算工期。

### 8.2 主要风险与应对

工具未被调用时，先核查宿主加载、工具描述和路由，不假定插件能强制拦截。上下文过时导致误用时，通过有效期、用户纠正及关键事实重查降低风险。工具增加时延时，减少非必要调用并比较实际成本。平台能力不同则缩小兼容声明，优先验证一个宿主。

### 8.3 待确认决策

- 首个试点宿主及其具体版本；建议先选当前最常用环境。
- 首个真实只读数据源、访问方式、字段定义和脱敏要求。
- 是否启用跨会话持久化，以及有效期、清除与日志保留策略。
- 首版发布形式、维护责任及评估门槛是否接受。
- 后续是否确实需要人员目录与业务写操作，分别由谁提供接口和授权。
